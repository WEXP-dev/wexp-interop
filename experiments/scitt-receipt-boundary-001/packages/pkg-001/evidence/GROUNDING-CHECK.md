# Pre-PR check: boundary grounding of the four inputs against Core-02 section 7

Checked on the frozen inputs of this package (payload digests pinned in `SOURCE-MANIFEST.json`).
Rule applied: the emulator verifies no issuer signature, applies no registration policy and signs
with a self-signed service certificate of the same run, so the grounding class may not exceed
`attributed`, and `status = supported` is admissible only under an evaluation context that
explicitly accepts that class. `attested` anywhere, or `supported` without the context clause,
would be a mapping error requiring a new derivation and run.

| input | status | grounding | target_binding | evaluation context | section 7 sentence relied on |
|---|---|---|---|---|---|
| a | supported | attributed | supported | `C-scitt-001`, trust `scitt-receipt-boundary-001-trust-1` (defined by the mapping as accepting `attributed`) | "An asserted-only or attributed finding can be supported only when the evaluation context explicitly accepts that grounding class; the result still reports the weaker grounding and its limitations." and "a valid signature associated with an accepted identity can make it attributed" |
| b1 | supported | attributed | supported | same | same |
| b2 | supported | attributed | supported | same | same |
| c | not-evaluated | not-evaluated | supported | same | "When status = not-evaluated, no base is added and the appraiser records E_BOUNDARY_NOT_EVALUATED." Pairing per section 6: "grounding = not-evaluated is valid only with status = not-evaluated". |

Findings:

- `attested` does not occur in any input or in `MAPPING.md` as a chosen value; the mapping says
  "Not `attested`: no boundary-grounding profile applies."
- Every `supported` boundary is under the context that the mapping defines as accepting
  `attributed`, and the mapping quotes "The evaluation context MUST identify the minimum
  acceptable grounding." The context clause is present.
- `attributed` rests on the one clause of section 7 that admits it: the receipt signature over the
  Merkle root was checked against the node certificate, and that certificate against the service
  certificate the relying party accepted. The acceptance is by fiat of the same operator; section 7
  says "Attribution is not proof of actual boundary control", and the mapping carries the
  circularity as a defect under the single limitation atom.
- A stricter reading would call this grounding `asserted-only`, on the view that a self-signed
  certificate generated by the same run is not an "accepted identity" in any meaningful sense.
  That reading is not what the inputs encode. Changing it would mean a new derivation and a new run
  (a new package or card revision with re-frozen expectations); under the check rule above it is
  not required, because `attributed` is within the admissible ceiling and the context clause holds.
  The alternative is recorded here so that a reviewer can choose it deliberately for package 002.

Conclusion: no mapping error under the stated rule; no change to inputs or expectations.
